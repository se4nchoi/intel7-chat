## P1 — 작성 내용과 운영 권한

### F01. 작성 중 내용이 다른 대상의 입력창으로 이동한다

**실제 UI 재현.** 학생으로 박학생의 DM을 열고 `박학생에게만 전달할 비공개 초안`을 입력한 다음 공개 `전체 대화` 채널을 선택했다. 공개 채널의 입력창에 그 문장이 그대로 남았다. 전송하면 공개 채널에 게시할 수 있는 상태다. 실제 공개 전송은 하지 않았다.

Q&A에서도 105번 질문의 답변 초안을 입력하고 목록으로 돌아가 104번 질문을 열면, 105번에 대한 답변 초안이 104번 질문의 답변 입력창에 남았다.

- 근거: `frontend/src/main.js:351`의 `selectChannel`, 질문 상세 전환 및 공유 폼. 대상별 초안 저장/복원이 없다.
- 증거: [비공개 초안이 공개 입력창에 남은 화면](../data_dev/ui-audit/private-draft-in-public.png), `extended-results.json`의 `draft-private-to-public`, `answer-draft-changes-question`.
- 수정 기준: 채널/DM ID 및 질문 ID별 초안을 분리한다. 새 대상에서는 그 대상의 초안만 복원하고, 대상 변경 중 진행 중이던 전송 결과가 새 대상의 초안을 지우지 않아야 한다.

### F02. 메시지 수정이 Markdown 원문 대신 렌더링 결과를 저장한다

**실제 편집 및 저장까지 재현.** 원문은 다음과 같았다.

````text
**중요 안내**
```python
print("hello")
```
@inst 코드와 서식을 확인해 주세요.
````

편집기에 들어간 내용은 `중요 안내python복사print("hello")@inst 코드와 서식을 확인해 주세요.`였다. ` 추가 설명`을 붙여 저장한 뒤 API로 다시 읽었을 때도 이 손상된 문자열이 저장되어 있었다. 감사 데이터의 원문은 확인 후 복구했다.

- 근거: `frontend/src/main.js:630`은 `.msg-text.textContent`를 읽는다. 코드 언어명과 복사 버튼의 문구가 섞이고 줄바꿈·Markdown 구분자가 사라진다.
- 증거: [서식 메시지 편집기](../data_dev/ui-audit/formatted-edit.png), `confirmation-results.json`의 `formattedSaved`.
- 수정 기준: 서버가 준 `message.body`를 편집 원문으로 사용한다. 코드 블록·굵게·링크·멘션·줄바꿈을 포함한 저장 왕복 검증이 필요하다.

### F03. 구성원 변경 폼이 강사 보호 규칙을 우회한다

**실제 관리 UI와 서버 결과로 재현.** 관리자 세션에서 `peer`를 강사로 지정했다. 다른 강사 `inst`가 수강반 관리의 `구성원 추가`에 `peer`를 입력하고 역할 `수강생`으로 저장하자 HTTP 201이 반환됐고 실제 역할이 student로 변경됐다.

같은 강사의 `내보내기` 경로는 다른 강사를 보호한다. 역할 변경 경로에서도 기존 강사에 대한 보호가 필요하다.

- 근거: `app/hub/routes.py:279`은 **새 역할이 instructor인 경우만** 관리자 권한을 요구한다. `app/hub/db.py`의 `add_membership`은 기존 역할을 그대로 덮어쓴다. `app/hub/routes.py:789`의 제거 경로에는 기존 강사 보호가 있다.
- 증거: `workflow-results.json`의 `instructor-can-demote-instructor` — `updateStatus: 201`, `peerRole: student`.
- 수정 기준: 기존 역할과 새 역할을 서버에서 함께 검사한다. 강사의 다른 강사/자신에 대한 역할 변경 정책을 명시하고 UI와 서버 모두에 적용한다. 변경 후 기존 탭의 역할 표시와 관리 컨트롤도 갱신한다.

## P2 — 기록, 탐색, 상태 및 접근성

### F07. 질문을 보고 있어도 새 강사 답변이 나타나지 않는다

### F09. 새 메시지를 보지 않았어도 약 0.8초 뒤 읽음 처리한다

학생이 메시지 영역 맨 위(`scrollTop: 0`)에 있는 상태에서 다른 강사가 새 메시지를 보냈다. 300/600 ms에는 unread=1이었고 900 ms에 unread=0, last_read_id가 새 메시지 ID로 바뀌었다. 화면에는 여전히 `↓ 새 메시지 1개`가 표시됐다.

- 증거: `confirmation-results.json`의 `unread.timeline`.
- 수정 기준: 읽음의 의미를 가시 영역/하단 도달/명시적 읽음과 일치시키고 새 메시지 표시와 배지가 충돌하지 않게 한다.

### F10. dialog 안의 오류를 dialog 밖 toast에 표시한다

학원 관리에서 이미 있는 `stu` 계정을 만들었다. `이미 사용 중인 아이디입니다.` 오류가 생성됐지만 네이티브 dialog 뒤에 가려졌다. toast 중앙 좌표의 최상단 요소는 toast가 아닌 계정 목록의 `.who`였다.

- 증거: `workflow-results.json`의 `modal-form-error-visibility`, [가려진 폼 오류](../data_dev/ui-audit/modal-error-hidden.png).
- 수정 기준: dialog 내부의 폼 오류/오류 요약과 필드 연결을 제공한다. 성공 안내와 실패 안내도 해당 작업 영역에서 확인할 수 있어야 한다.

### F11. 세션 폐기 후에도 앱과 쓰기 입력이 활성 상태로 남는다

브라우저에서 로그아웃 API를 직접 호출해 세션 폐기를 재현했다. 소켓은 닫히고 재로그인 안내가 나왔지만 앱 화면은 유지되고 입력창도 활성화돼 있었다. 로그인 폼은 숨겨져 있고 보이는 로그인 버튼도 없었다.

- 근거: `frontend/src/main.js:475`의 1008 close 처리는 toast만 표시한다. 실제 시간 경과에 의한 만료는 기다리지 않았고 같은 처리 경로를 소스로 대조했다.
- 증거: `workflow-results.json`의 `expired-session-ui`.
- 수정 기준: 쓰기를 중단하고 명시적인 재로그인 동작을 제공한다. 초안은 안전하게 보관하고 재인증 후 올바른 대상에서 복원한다.

### F12. 앱 초기화 실패와 미로그인을 구분하지 않는다

초기 `/me` 요청에 503을 주입했더니 아무 오류 설명 없이 정상 로그인 화면이 표시됐다. 사용자는 서비스 장애를 비밀번호 문제로 오해할 수 있다.

- 근거: `frontend/src/main.js:179`의 `boot`는 `/me`의 모든 실패를 같은 catch에서 처리한다.
- 증거: `workflow-results.json`의 `boot-network-failure`.

### F13. 자료 로드 실패가 비어 있는 자료실처럼 보인다

파일 목록 API에 503을 주입했다. 일시적인 전역 toast만 표시되고 파일 영역은 비어 있었다. 화면 안에 오류 상태나 목록 재시도 버튼이 없고 업로드 폼은 계속 보인다.

- 증거: `audit-results.json`의 `failed-files-no-retry`, [자료 로드 실패](../data_dev/ui-audit/failed-files.png).
- 수정 기준: loading / empty / error / ready 상태를 구분하고 각 영역 안에서 재시도할 수 있게 한다. 같은 패턴을 채널 기록·질문·구성원 로드에도 적용한다.

### F14. 긴 채널명이 사이드바 안을 가로로 밀어낸다

긴 채널을 선택한 뒤 사이드바 내부는 clientWidth=259, scrollWidth=644, scrollLeft=385였다. 다른 채널명의 앞부분과 선택 표시가 화면 밖으로 밀려났다. 문서 전체 가로 넘침 검사에서는 잡히지 않는다.

- 근거: `.side-scroll`, `.channel-list` 및 그리드/플렉스 자식의 최소 크기 제한.
- 증거: `workflow-results.json`의 `nested-sidebar-and-avatar-layout`, [내부 가로 넘침](../data_dev/ui-audit/nested-overflow-and-avatar.png).
- 수정 기준: 사이드바 및 항목의 `min-width`와 가로 overflow를 제한하고 전체 이름은 툴팁/접근 가능한 이름으로 보완한다.

### F15. 긴 구성원 이름이 아바타와 접속 표시를 자른다

32 px 아바타를 감싸는 `.presence-wrap`의 실제 폭이 약 10.98 px로 줄어들었다. 아바타가 부분적으로 잘리고 접속 표시도 부자연스럽다.

- 증거: F14와 동일한 JSON/스크린샷.
- 수정 기준: 아바타/접속 표시 영역은 축소하지 않고 이름 영역만 말줄임한다.

### F16. 닫힌 모바일 메뉴 안으로 Tab 포커스가 들어간다

390 px 화면에서 닫힌 메뉴 상태로 Tab을 누르자 `.rail-home`에 포커스가 갔다. 그 요소의 x는 -74.4, 오른쪽 끝은 -26.4 px로 화면 밖이었다.

- 증거: `audit-results.json`의 `mobile-drawer-keyboard`.
- 수정 기준: 닫힌 메뉴의 포커스 진입을 막고, 열기/닫기 때 포커스 이동과 복원을 명시한다.

### F17. 일반 메시지의 작업 버튼을 키보드로 열 수 없다

일반 텍스트 메시지 행은 tabindex=-1이고 내부의 유일한 버튼은 visibility:hidden인 반응 버튼이었다. 행에 도달할 키보드 진입점이 없어 `:focus-within`으로 작업창을 드러낼 수 없다. 서식 메시지의 코드 복사 버튼이 우연한 진입점이 되는 경우와 구분된다.

- 근거: `frontend/src/main.js`의 `messageActions`, `frontend/src/style.css:287`.
- 증거: `audit-results.json`의 `message-keyboard-actions`.
- 수정 기준: 키보드로 접근 가능한 메시지 작업 메뉴 또는 행 포커스 패턴을 제공한다. [W3C 키보드 접근성 기준 설명](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)을 참고한다.

### F18. 작은 보조 텍스트의 대비가 충분하지 않다

답변 빈 상태의 13 px 문구는 라이트 테마에서 약 3.006:1, 다크 테마에서 약 3.539:1이었다. 일반 크기 텍스트의 4.5:1 기준에 미달한다. 계산은 브라우저가 반환한 전경/배경 색을 사용했다. `aria-hidden`인 아바타 글자는 이번 결함 판정에서 제외했다.

- 근거: `frontend/src/style.css:217`의 `.empty-answer`와 `--faint` 토큰.
- 증거: `contrast-results.json`, `extended-results.json`의 contrast 샘플.
- 수정 기준: 보조색 토큰을 조정하고 실제 사용 배경별로 확인한다. [W3C 명암 대비 기준 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

### F19. 강사의 ‘입력하거나 선택’에는 실제 선택지가 없다

강사 관리창에 구성원이 35명 있었지만 `#membership-options`의 option 수는 0이었다. 계정 선택지는 관리자만 실행하는 `loadAccounts`에서 채워진다. 강사는 기존 계정 아이디를 정확히 알아야 한다. 구성원 목록 자체의 검색도 없다.

- 근거: `frontend/src/main.js:1096`과 역할별 `refreshManagement`.
- 증거: `extended-results.json`의 `instructor-membership-options`, [강사 관리 목록](../data_dev/ui-audit/instructor-management-populated.png).
- 수정 기준: 강사에게 허용된 범위의 검색/초대 흐름을 설계하거나, 실제 동작에 맞는 입력 안내를 제공한다. 전체 학원 계정 노출 여부는 별도 권한 정책으로 결정한다.

### F20. 긴 관리 목록을 읽으면 관리 탭이 화면 밖으로 사라진다

계정 목록 끝까지 스크롤했을 때 관리 탭의 y는 -3436 px였다. 닫기 헤더는 남아 있지만 내 계정/수강반/학원 관리 전환을 위해 긴 거리를 다시 올라가야 한다.

- 근거: `.dialog-head`는 sticky지만 `.management-tabs`는 아니다.
- 증거: `confirmation-results.json`의 `managementScroll`, [스크롤 후 관리 탐색](../data_dev/ui-audit/management-tabs-scrolled-away.png).
- 수정 기준: 작업 탐색은 고정하고 긴 목록에 별도 스크롤/검색/필터/페이지를 제공한다. 관리 대상 수강반명도 창 안에서 명확히 보여준다.

## P3 — 상태 표현과 안내

### F21. Escape로 구성원 패널을 닫은 뒤 aria 상태가 남는다

- 증거: `audit-results.json`의 `memberAria`.
- 수정 기준: 모든 닫기 경로에서 DOM/접근성 상태를 같은 함수로 갱신한다.

### F22. 수강반이 없는 관리자에게 학생용 안내가 나온다

관리자에게 빈 수강반 응답을 주입하면 `강사에게 참여 권한을 요청하세요`라고 안내한다. `학원 관리` 버튼은 있어 생성이 막힌 것은 아니지만 초기 설정의 다음 단계가 명확하지 않다.

- 증거: `audit-results.json`의 `empty-admin-onboarding`, [관리자 초기 화면](../data_dev/ui-audit/empty-admin.png).
- 수정 기준: 관리자에게 수강반 만들기, 강사에게 배정/개설, 학생에게 참여 요청을 안내한다.

## 별도 제품 범위로 결정할 항목

아래는 현재 제공한다고 약속된 동작이 깨진 사례와 분리했다.

- **자료 관리:** 자료 검색·분류·미리보기·삭제/보존 정책. 질문 삭제 후 첨부 자료를 수강반 자료실에 계속 남길지 명시해야 한다.
- **탐색과 알림:** 채널/DM/질문/자료실/필터의 공유 가능한 주소, 질문 팔로우와 답변 알림, 채팅 검색.
- **운영:** 수강반/채널 이름·설명 수정, 계정/구성원 일괄 처리와 초대 흐름, 활성/소속별 계정 필터.
- **개인 설정:** 표시 이름 변경, 세션 목록/기기 로그아웃, 계정 복구/문의 경로.
- **모바일 읽기 밀도:** 허용 최대 길이의 질문 제목은 320 px에서 첫 화면 대부분을 차지한다. 질문 제목·본문·작업의 정보 우선순위를 추가로 다듬을 수 있다.

## 권장 수정 순서와 완료 조건

1. **F01–F03:** 대상별 초안 격리, 원문 기반 메시지 편집, 기존/새 역할을 함께 검증하는 서버 권한 규칙. 잘못된 대상 전송과 역할 변경을 막는 회귀 검사를 추가한다.
2. **F04–F09:** 기록·질문 단건 조회·검색·페이지 이동·히스토리·읽음 정책을 정리한다. 100개 초과 데이터와 두 사용자 세션에서 확인한다.
3. **F10–F13:** 폼/영역/인증의 loading, error, retry, reauthenticate 상태를 화면 안에서 완결시킨다.
4. **F14–F18:** 내부 넘침과 축소, 키보드 진입/복원, 대비를 고친다. 320 px와 다크 모드뿐 아니라 실제 키보드/보조기술에서도 확인한다.
5. **F19–F22:** 역할별 작업 탐색과 초기 안내를 다듬고 제품 범위 항목을 우선순위화한다.

## 증거, 재현 환경 및 한계

증거는 Git에서 제외된 `data_dev/ui-audit/`에 있다.

- `audit-results.json`: 초기 핵심 워크플로, 기록 제한, 뒤로가기, 키보드 검사.
- `extended-results.json`: 30개 반응형·테마 조합, 대상별 초안, 역할별 목록, 미배정 사용자, dialog 포커스.
- `workflow-results.json`: 권한 변경, 세션 폐기, 중복 계정 오류, 초기 장애, 내부 넘침/아바타 측정.
- `confirmation-results.json`: 실제 저장된 메시지 손상, 300 ms 간격 읽음 상태, 관리 탭 위치의 재확인.
- `contrast-results.json`: 샘플 색과 대비 계산.
- 스크립트: `data_dev/run_ui_audit.py`, `comprehensive_ui_audit.cjs`, `extended_ui_audit.cjs`, `workflow_ui_audit.cjs`, `confirm_ui_audit.cjs`, `crud_ui_audit.cjs`.

첫 다중 컨텍스트 스크린샷 검사에서 브라우저 크래시/캡처 타임아웃이 발생했다. 한 번에 하나의 컨텍스트를 사용하는 후속 검사에서 30개 조합을 모두 완료했고 해당 매트릭스의 브라우저 JS 오류는 0건이었다. 편집 중 텍스트로 행을 찾던 감사 스크립트의 선택자도 메시지 ID 기반으로 바꿔 일반 메시지 수정/삭제를 재확인했다. 이 도구 문제들은 제품 결함으로 집계하지 않았다.

실제 휴대폰의 가상 키보드, Safari/Firefox, 화면낭독기 전체 흐름, 브라우저 확대율, 장시간 동시 사용 및 대규모 부하 검사는 하지 않았다. 별도 접근성 검사 라이브러리 없이 DOM/키보드/색 샘플을 확인했으므로 WCAG 전체 적합성 판정을 의미하지 않는다. 화면 공유는 범위에서 제외했다.
